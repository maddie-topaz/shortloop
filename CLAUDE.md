# shortloop

URL shortener built as a testbed for an agentic DevOps pipeline. The pipeline is the point; the app is deliberately small.

## Layout

npm workspaces monorepo:

- `backend/` — Express + TypeScript API, Postgres via `pg`
- `frontend/` — React + TypeScript + Vite, styled with daisyUI (Tailwind v4)
- `infra/` — Pulumi (TypeScript) program: ECS Fargate + RDS + ALB
- `scripts/dev.sh` — starts Postgres, backend, and frontend together

## Commands

```bash
npm run dev          # Postgres (docker) + backend + frontend, one command
npm run dev:down     # tear down the Postgres container
npm test             # both workspaces
npm run build        # both workspaces
```

## Conventions

- Backend routes are registered in `backend/src/app.ts`. `createApp(store)` takes a `LinkStore`, so the route tests inject a mock and never need a database.
- `PgStore` is the only `LinkStore` implementation. Any new persistence method goes on the interface in `backend/src/store.ts`, is implemented in `PgStore`, and needs a case in `backend/tests/pgStore.integration.test.ts` — that file is the only thing that exercises real SQL, so an untested method there is an untested method in prod.
- Backend tests need Postgres (`docker compose up -d`). Mutation testing does not: `backend/jest.stryker.config.js` excludes `*.integration.test.ts`, keeping the Stryker run in-process and parallel. Do not point it at a database — parallel mutant workers share one `links` table and truncate it out from under each other, which makes the score nondeterministic.
- `GET /:code` is a catch-all and must stay the **last** route registered, after static file serving and all `/api/*` routes.

## Gotchas that cost real debugging time

- **RDS requires SSL.** `backend/src/index.ts` sets `ssl: { rejectUnauthorized: false }` when `NODE_ENV=production`. Removing it produces `no pg_hba.conf entry ... no encryption` and the container exits on boot.
- **Backend serves the frontend in production.** The Dockerfile copies `frontend/dist` to `backend/public`, and Express serves it via `express.static`. Locally that directory doesn't exist, which is fine — the Vite dev server serves the frontend instead and proxies `/api` to the backend.
- **Backend dev port is 4000, not 3000.** 3000 is commonly occupied.
- **GitHub's OIDC `sub` claim includes immutable IDs** (`repo:owner@123/repo@456:...`), not just names. The AWS IAM trust policy for `shortloop-github-actions` matches both forms. Renaming or transferring the repo will change these IDs and break deploys until the trust policy is updated.

## Deployment

Merging to `main` triggers `.github/workflows/deploy.yml`, which builds the image, pushes it to ECR tagged with the commit SHA, and runs `pulumi up` against the `prod` stack. There is no manual deploy step.

`imageTag` is a **required** stack config value with no default, and it is not committed — CI supplies it per run. Any Pulumi command therefore needs `--config imageTag=<sha>`, and passing the wrong value rolls production onto that image. It used to default to a fixed tag, which meant a local `pulumi up` silently rolled production back; requiring it makes that failure loud instead.

The GitHub Actions OIDC provider, its IAM role, and that role's policy attachment are Pulumi-managed (adopted via import). Changing who can assume the deploy role is a reviewable diff, not a console click.

## Rules

- **Never push directly to `main`.** Branch protection enforces this; work on a branch and open a PR.
- **Never merge your own PR.** A human reviews and merges.
- **Never run `pulumi up` or `pulumi destroy` against `prod` from a local machine.** Deploys go through CI so the state and image tag stay consistent.
- **Never widen the database security group.** `shortloop-db` accepts traffic only from the service security group. It should never accept `0.0.0.0/0`.
- **Never commit credentials.** AWS keys, Pulumi tokens, and database passwords belong in GitHub secrets or Secrets Manager. The RDS password is generated by Pulumi and stored in Secrets Manager; it should never appear in code, config, or a task definition's plain environment variables.
- **Keep diffs small.** A large PR is an unreviewable PR, and unreviewed code is the actual risk.
